# Plan: speed up navigation from published HTML to the hub

Status: investigation and proposed design, not authorization to implement. No live service was restarted or reloaded. A live restart or reload requires a separate fresh explicit “restart now” authorization. Do not reset live fixtures or registrations.

## Evidence and blockers

The [handoff](slow-html-navigation.md) records a 14.9 ms navigation action followed by an 18,859,821-byte, uncompressed, `no-store` HTML response: 2,026 ms waiting, 1,274 ms receiving, and first contentful paint at about 3,475 ms. This is one prior capture on revision `70bed85b`, not a new measurement. Its waiting time cannot distinguish server work from tunnel or network costs; the route in that capture has not been independently identified. Do not claim a root cause or a measured speedup.

The code traces the likely path: `src/hub-runtime.mjs:119-140` writes published siblings whose links to built-in views target `hub.html`, awaiting `navigate` before setting location. Lines 179-186 select the view; lines 204-212 embed both bundles in the generated hub and register it with Lavish. `vendor/lavish/src/server.js:2353-2438` reads and verifies a path-addressed HTML page, injects the SDK, and sends it `no-store`; lines 2302-2350 handle the legacy entry. The authored-resource service in `src/hub-transport.mjs:21-39` is a different path. The captured request must still be classified safely before attributing its delay to either Lavish handler.

In this workspace, `wc -c dist/diff-app.js dist/hub-markdown.js` reported 8,368,945 and 10,452,292 bytes, respectively, or 18,821,237 bytes together. These are existing local build artifacts, not a fresh build or proof of the live version. `build.mjs:23-40` embeds the portable worker into the diff bundle and builds the Markdown bundle separately. `web/diff-app.mjs:24-34` starts that worker at script load. The inline bundles account for most of the captured HTML size by comparison, but their presence alone does not prove the two-second wait's cause.

Export is a constraint, not a solved detail. `vendor/lavish/src/export-bundle.js:49-50` sets a 10 MiB per-asset and 25 MiB total default limit. The local Markdown bundle is only 33,468 bytes below the per-asset limit. External module scripts and inline module imports remain references (`export-bundle.js:2530-2540, 2790-2810`), so dynamic `import()` cannot be assumed to produce a portable export. The existing export suite passed 151 tests in this investigation, but it does not prove a future lazy loader exports correctly.

Blocking decisions: an isolated end-to-end route/timing probe and export prototype were not completed. The capture's exact handler, the amount of server versus tunnel delay, and a defensible time target remain unknown. Do not present this plan as an approved implementation or a verified performance fix. The owner must approve the numerical target after the baseline below; a live restart remains separately authorized.

## Proposed design and feasibility gates

1. Run the measurement contract below in an isolated temporary workspace, with a separate Lavish state directory and ephemeral ports. Classify the document route without recording its URL, query, headers, body, capability, or private path. Instrument arrival, resolution, read, SDK injection, headers and finish using an opaque request ID and route category. Compare local and tunnel runs. Also generate esbuild metafiles to identify the worker, grammars and duplicated dependencies. Do not change the live service.
2. Preferred implementation: keep configuration and page HTML inline and `no-store`, but write the two classic IIFE build outputs as content-hashed sibling files under the generated artifact directory. Use a narrowly allowlisted immutable asset response for only verified build-produced hashes; the existing generic sibling route (`server.js:2442-2528`) has `public, max-age=0` and must not gain a blanket immutable policy. Keep authored resources and capability-bearing data outside that allowlist. Retain each referenced hash for the lifetime of the generated hub directory, including across owner restarts and upgrades; install with atomic create/rename before publishing HTML, never overwrite hash contents, and delete only with explicit whole-hub cleanup after no session uses it. This deliberately favors correctness over automatic disk reclamation. Test old-page loads after generating a newer page and after restart.
3. Lazy-load classic scripts using a single shared promise per bundle, with error, retry and selection-generation guards. Defer worker creation until a diff view mounts; retain fallback and clean up blob URLs. Preserve confirmation and capture destinations before awaits, annotation SDK behavior, save targets, and `docs/feedback-routing.md` delivery guarantees. Validate the real sandboxed opaque-origin browser before choosing exact script/CORS attributes. No global cache policy or module imports are assumed.
4. Export gate: ordinary dynamically inserted script tags are not present in source HTML for the export inliner to discover. Before implementation proceeds, prototype a static, confined classic-script reference representation that export can inline while the live page defers execution, including the loader's exported behavior. Verify it in an offline browser with no server and with both views selected. Alternatively implement an explicit export transform that replaces known generated loader references with bounded, escaped inline scripts. Either approach must honor the 10 MiB per-asset and 25 MiB total caps, SDK stripping, symlink confinement, and no outbound export requests. If neither can meet those constraints, stop and obtain a portability decision; do not silently ship a broken export or lift caps globally. Treat current hub actions requiring a running owner separately from self-contained rendering and state exactly which functions remain unavailable offline.
5. Compression is optional, not a condition of the preferred design. Only consider it if the same measurements show transfer remains a material bottleneck. If selected, limit it to explicitly identified responses, implement `Accept-Encoding` negotiation, `Vary`, identity fallback and correct lengths, and retain `no-store` on private HTML. Compression does not establish a response-start improvement. If response-start remains dominant, diagnose the measured component instead of treating transfer reduction as its fix.

## Measurement contract

Use a fresh temporary repository, fixed generated published HTML fixture and representative commit/diff and Markdown fixtures, same revision and generated dist dependencies on each side. Record OS, machine class, Node and browser versions, build command and lockfile revision, viewport, tunnel type and configuration category, test revision and fixture byte counts. Do not record private paths, URLs, headers, bodies, tokens or capture files in the repository. Run baseline and candidate on the same machine and network, alternating their order. Use Chrome with cache enabled, no throttling, a fresh browser profile for cold runs, and a primed profile for warm runs. Run at least 10 transitions per condition after one discarded warm-up, both loopback and the representative tunnel; repeat the exact published-HTML-to-Commits click.

Record action completion, document request start, response start and end, encoded and decoded bytes, FCP, and the first visible Commits heading. Record server phase durations with a monotonic clock, including request arrival to first headers and finish. Report median, p90 and all individual samples; label missing or failed samples and do not replace them silently. The proposed release target is at least 50% lower median click-to-visible-heading on warm tunneled runs, with no more than 10% regression in local median and no failed transitions. This is a proposed target, not an observed result or an approved requirement. The operator must approve or change it after reviewing baseline variance. Do not infer server timing from browser TTFB or sum nested parse/evaluation events.

## Numbered acceptance criteria and test mapping

The names below are proposed new test names, not tests already present. Implement them in the listed files. Commands run from the repository root, sequentially in an isolated checkout. Browser prerequisites follow `TESTING.md` and the full checks remain required.

1. Route and timing evidence: `route classification and phase timings` in `test/hub-navigation-perf.test.mjs` checks route-category correlation, ordered monotonic phases and redaction with a temporary isolated server. The measurement report contains the contract's environment, all samples, local/tunnel comparison and exact route classification. Command: `node --test test/hub-navigation-perf.test.mjs`. Until the representative tunnel capture is available, this criterion is blocked, not passed by a unit test.
2. Small private document and safe assets: `hub emits versioned assets without embedding bundles` and `only generated hashes are immutable` in `test/hub-assets.test.mjs` assert both bundles absent from HTML, private HTML `no-store`, exact allowlist, content-hash integrity, traversal/symlink denial and arbitrary sibling cache policy unchanged. Set an explicit 256 KiB maximum generated HTML fixture size and assert both bundles' size independently. Command: `node --test test/hub-assets.test.mjs`.
3. Retention: `old hub assets survive upgrade and owner restart` in `test/hub-assets.test.mjs` creates two generations, restarts only its isolated owner, and loads each original hash; cleanup occurs only at whole-hub deletion. Same command as criterion 2.
4. Navigation and lazy loading: `published navigation loads selected view and retries` and `late bundle completion cannot change selection` in `test/hub-browser.test.mjs` cover all built-in views, warm revisit, failure/retry, delayed load and rapid selection, dirty confirmation with edits during awaits, the opaque-origin iframe and SDK. Command: `node --test test/hub-browser.test.mjs`. Add an assertion that Markdown is not fetched before its view and diff worker starts only on diff mount.
5. Export and worker: `generated lazy hub exports offline` in `vendor/lavish/test/export-bundle.test.js` covers confined classic assets, escaping, SDK removal, no outbound requests, both lazy views offline, budget overflow and symlink escape. Add `diff worker fallback and cleanup` in `test/hub-browser.test.mjs`. Commands: `node --test vendor/lavish/test/export-bundle.test.js` and `node --test test/hub-browser.test.mjs`. A real offline browser check is required in addition to static export assertions; document any owner-dependent actions.
6. Existing behavior: `hub navigation retains destination and save guards` in `test/hub-browser.test.mjs` covers authored resources, annotation controls, fresh configuration and save-target capture after asynchronous selection. Run `node --test test/hub-browser.test.mjs test/hub-documents.test.mjs` and `node test/hub-e2e.mjs` with the documented isolated `hc` prerequisites.
7. Compression only if implemented: `encoding negotiation and private cache policy` in `test/hub-assets.test.mjs` checks gzip/Brotli as implemented, identity and unsupported encoding, `Vary`, decompressed equality, correct length and cache headers. Command: `node --test test/hub-assets.test.mjs`. If compression is not implemented, mark this criterion not applicable, not failed or passed.
8. Performance: the measurement report meets the operator-approved target using the measurement contract and reports bytes and phase timings even if the target fails. Run the reproducible benchmark command added with criterion 1, `node test/hub-navigation-perf.mjs`, once per recorded baseline/candidate condition. This benchmark is proposed and does not exist yet. Do not replace real browser/tunnel measurements with a unit test.
