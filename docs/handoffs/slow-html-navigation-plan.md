# Plan: speed up navigation from published HTML to the hub

Status: proposed, not approved. No runtime changes have been made. Preserve the live session and do not restart or reload it without a fresh explicit “restart now” authorization. Do not reset its fixtures or registrations.

## Evidence and uncertainty

The prior capture in [the handoff](slow-html-navigation.md) reports a 14.9 ms navigation action, followed by an 18.86 MB uncompressed, `no-store` HTML response with 2.03 s waiting and 1.27 s receiving. First contentful paint occurred about 3.47 s after navigation began. These are prior measurements, not measurements of the current workspace. Waiting and receiving dominate that capture, but the waiting time cannot be attributed to a particular component yet. Snapshot latency is separate.

`src/hub-runtime.mjs:119-140` generates published sibling pages whose built-in view links target `hub.html`, then sends a `navigate` action before changing location. Lines 179-186 validate and store the selection. Lines 204-212 read both built bundles, inline them in the generated hub page, write that page, and register it with Lavish. `build.mjs:23-40` bundles the portable worker into the diff bundle as a string, disables splitting for that bundle, and independently bundles the Markdown entry. `web/diff-app.mjs:24-34` creates a blob worker and initializes it at script load, while `web/document-controls.mjs:1-9` imports Markdown and syntax-highlighting dependencies. These facts explain where to investigate size, but do not establish the dependency-level byte breakdown.

In the vendored server, `vendor/lavish/src/server.js:2353-2438` resolves a path-addressed HTML page, reads the whole file, verifies the active load, injects the SDK and sends `no-store` HTML. The legacy entry takes a similar path at lines 2302-2350. The asset path at lines 2442-2528 instead confines and streams files with `public, max-age=0`; it is not an immutable-cache service. `src/hub-transport.mjs:21-39` serves authored resources separately. The code supports the likely route, but the private capture has not been checked for a safe route classification, so the exact captured handler remains unverified.

## Implementation sequence

1. Reproduce in a separate temporary workspace and service, never the live demo. Record revision, environment, payload sizes and at least five warm runs of the same published-HTML-to-Commits transition locally and through the same tunnel. Record action duration, request start, response start/end, first contentful paint and visible heading time. Use medians and ranges, distinguish cold from warm cache, and do not log URLs, query strings, headers, bodies, tokens, or private file paths. Correlate by a generated request ID and route category only. Obtain safe timings around server arrival, page resolution, file read, SDK injection, response headers and finish, plus byte counts. Confirm whether the path-addressed or legacy handler serves the measured page. Compare with a local request to separate server work from transport without asserting a cause from browser waiting alone.
2. Generate esbuild metafiles or equivalent local size reports for each entry and its embedded worker, including duplicated syntax grammars and highlighter code. Compare raw and encoded transfer sizes. Keep reports free of private contents. Establish the largest contributors before deciding whether dependency reduction or lazy loading is worthwhile.
3. Prototype moving only build-produced, non-secret JavaScript bundles out of the generated HTML. Keep runtime configuration and capability-bearing HTML `no-store`. Prefer content-hashed names and immutable caching only on a narrowly scoped, explicitly allowlisted route for those exact build outputs; do not grant immutable caching to arbitrary authored sibling files. Define update and cleanup behavior so an existing page can still load its matching bundle during a rolling update. The current sibling route is insufficient for immutable caching, and the sandboxed opaque-origin iframe may require appropriate CORS headers for scripts or modules. Test actual browser behavior before choosing module loading. Preserve export portability: use a confined same-directory asset arrangement that the existing export inliner can include, or retain a portable inline export path. Verify the choice rather than assuming exported pages can fetch local services.
4. Load the diff and Markdown code only when their views need it, with a shared in-flight promise, explicit failure/retry UI, and race guards so a late load cannot mount a view after selection changes. Preserve draft confirmation and destination capture across awaits. Start the worker when the diff view actually needs it; retain its fallback and revoke blob URLs when safe. Avoid changing snapshot semantics or save routing. If the first view requires a bundle immediately, measure whether parallel preload helps rather than assuming lazy loading improves it.
5. If measurement still shows transfer as a bottleneck, add negotiated gzip or Brotli for the specific safe static assets and, separately, evaluate compression of the private HTML response without caching it. Respect `Accept-Encoding`, identity fallback, `Vary: Accept-Encoding`, correct lengths and content type, and error handling. Compression may lower receive time but does not establish a fix for response-start latency. If server instrumentation shows read or injection dominates, address that measured cost separately while preserving file verification, load-generation checks and SDK injection guarantees.
6. Repeat the baseline measurements on the same environment and transition with identical fixtures. Report before/after median and range for response start, transfer, first contentful paint and visible heading, plus actual wire bytes and asset cache hits. If results do not meet the agreed target, retain the measurements and revisit the bottleneck instead of claiming success.

## Acceptance criteria and verification

- The measured route and timing attribution are documented with safe, reproducible instrumentation. No private trace contents or capability URLs enter logs, tests, or committed files.
- The generated hub HTML no longer embeds the large diff and Markdown bundles, and tests enforce a size budget derived from the measured baseline. Only explicitly public build assets receive long-lived immutable caching; private HTML remains `no-store`. Version changes select new bytes, and a running older page can still load its assets.
- Browser tests cover published HTML to each built-in view and back, repeated navigation with a warm cache, slow and failed asset requests, retry, rapid selection changes, and edits made while navigation confirmation is pending. Verify visible loading/error feedback and the correct destination. Exercise the opaque-origin iframe and authenticated SDK.
- Test first use and subsequent use of diff and Markdown views, worker startup and fallback, authored sibling resources, local export without outbound requests, and update/restart behavior. Preserve annotation controls, fresh configuration, save-target guards, and the delivery guarantees in `docs/feedback-routing.md`.
- Test encoding negotiation, identity fallback, `Vary`, byte equality after decompression, cache headers, hash changes, route confinement and rejection of arbitrary files. Test macOS and Linux paths where applicable.
- The same measured transition improves against the recorded baseline, with a numerical target agreed before implementation. Report any unchanged response-start delay separately. Run repository-required `just check`, inspect the screenshot matrix at original size and `status.json`, and complete integration only under the shared integration lock with the required full QA.

## Decisions for the operator

- Approve the performance target and measurement environment after the baseline is collected. A fixed latency threshold chosen before local and tunneled baselines would be arbitrary.
- Approve the proposed asset and lazy-loading approach after the route, export, sandbox, and bundle-size probes. If preserving portable export requires a material behavior or packaging change, choose that tradeoff explicitly.
- Authorize any restart or reload of the live demo separately by saying “restart now”. Implementation experiments should use isolated services and need no live restart.
